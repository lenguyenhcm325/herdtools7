# `tests/het-x86` — the committed (x86_64, hip) pair fixture

Three het tests with an x86-64 CPU column, plus the two files the emitter
resolves beside them. It exists so that gates and cram tests which need the **(x86_64, hip)
pair** (`litmus/hetMachine.ml`) do not have to generate the whole 411-test
x86 corpus first — `tests/het/generate-x86.sh` needs `hetgen7` on `$PATH`, which a
cram sandbox does not have.

**`make hetlitmus-x86fixture` keeps it honest.** Everything here is an extract, so
it can go stale in silence while every gate that reads it keeps passing;
`hetlitmus/verify/x86fixturecheck.py` runs the generator into a temp dir and
compares the three `.litmus` files byte for byte and each map row verbatim. If it
reddens, **re-cut from a fresh run — do not edit these files to match.**

It is **not** a corpus. `corpus-gate.sh` counts `tests/het` and
`tests/gpu-only` only, and nothing here is generated by, or checked against,
`generate.sh`.

Three `.litmus` files, all copied verbatim from a `generate-x86.sh` run, so they
are the same renderings the real x86 lane emits:

* `MP-cg-sys-relaxed-x86_64.litmus` — `Canary=self` on the AMD lattice: this
  test **is** the Layer-B canary, so it co-runs nothing and is the single-instance
  case. It is also the canary the other two co-run, which is what closes the
  fixture at three files.
* `MP-cg-sys-acqrel-2s-x86_64.litmus`, `S-cg-sys-fence-x86_64.litmus` — the
  two-instance (T + canary) case, so the cram tests that read a `.hip` render see
  the co-run arena and not only the single-instance path. Both are `NO-ORACLE` on
  the AMD lattice and name no mu(T), which is why no mutant is needed here.

and the two files the emitter resolves beside them:

* `control-map-amd.csv` — their three rows, copied from the re-keyed map
  `generate-x86.sh` writes. This is the file the emitter reads for the oracle
  class, mu(T) and the canary.
* `expected-amd.csv` — their three rows, likewise. Nothing is parsed out of it:
  the emitter only tests that it EXISTS beside the test, because that is what
  makes the harness stamp `expected-amd.csv:AMD-CDNA3-x86` instead of
  `(no oracle CSV)`.

Both CSVs are three-row EXTRACTS of the committed originals in `tests/het`, not
independent judgements. Regenerate them from there if a row ever moves; the
originals stay the only place an AMD verdict is decided.
